# Situation Packs — product vision vs implementation

| Pack | Potential situation / inputs | Independent verification needed | Current state |
|---|---|---|---|
| Home | Rentals, deposits, listings, landlord representation | Authorized registry, independent ownership/authority, listings | H0: limited guidance only |
| Identity | Impersonated banks, employers, institutions | Official contact directories/identity providers | H0: limited guidance only |
| Web | Phishing, malicious forms, redirects | Safe URL reputation and authorized page context | Vision |
| Social | Conversational coercion, romance scams | Temporal, contextual signals and human-centered reviews | Research |
| Commerce | Fake stores, seller changes, escrow | Merchant checks, transaction constraints | Vision |
| Work | Recruitment fees, impersonated recruiters | Corporate domains/registry channels | Vision |
| Finance | Account changes, investment pressure | Bank/payment partner authorized data | Vision |
| Web3 | Wallet poisoning, risky approvals, crypto offers | RPC and licensed risk services | Vision |
| Cross-rail | Fiat/stablecoin/fiat context | Regulated partners, settlement proofs | Research |
| Response | After user has already acted | Country-specific vetted response playbooks | Vision (generic pause guidance only) |

Shared model: Case -> Event -> Claim -> VerificationReceipt -> Assessment -> Intervention. All future packs must prove both access rights to sources and benefit against a baseline. No personal reputation lists without governance and appeal process.
